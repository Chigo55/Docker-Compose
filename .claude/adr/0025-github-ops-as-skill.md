# ADR-0025: GitHub 운영은 절차를 스킬로 두고 대화로 진행한다

- 상태: Accepted
- 관련: [ADR-0016](0016-track-in-github-not-docs.md)(추적은 문서가 아니라 GitHub 으로 — 이 ADR 은 그 결정이 만든 부담을 다룬다), [ADR-0017](0017-ruleset-enforced-main-protection.md), [ADR-0020](0020-generate-release-notes-from-prs.md), [ADR-0024](0024-milestones-for-cross-cutting-goals.md), [ADR-0021](0021-generated-doc-index.md), [rules/github.md](../rules/github.md)

## 배경 (Context)

[ADR-0016](0016-track-in-github-not-docs.md)이 추적을 저장소 문서에서 GitHub 으로 옮겼다. 그 뒤로
GitHub 쪽 표면이 계속 넓어졌다 — Ruleset 강제([ADR-0017](0017-ruleset-enforced-main-protection.md)) ·
PR 라벨에서 릴리스 노트 자동 생성([ADR-0020](0020-generate-release-notes-from-prs.md)) ·
마일스톤([ADR-0024](0024-milestones-for-cross-cutting-goals.md)) · Project #4 의 커스텀 필드 ·
서브이슈 · Security 설정. 지금 이 저장소를 운영하려면 **이슈만 알아서는 부족하다.**

문제는 이 표면에 대해 저장소가 담고 있는 것이 **현황뿐**이라는 점이다.
[rules/github.md](../rules/github.md) 는 "무엇이 켜져 있는가" 를 잘 기록한다(필수 체크 이름, Actions
기본 권한이 `read` 라는 사실, dependabot 범위). 그러나 **"새 이슈를 받았을 때 무엇을 어떤 순서로
하는가"** 는 어디에도 없다. 그래서 매번 `gh` 명령을 즉흥적으로 조합하게 되고, 여러 단계 중 일부가
조용히 빠진다. 이 저장소에서 실제로 관찰된 누락:

- **Project 등록과 필드 입력이 이슈 생성과 별개 단계**여서 빠진다. #53·#59~#65 는 Project 에
  등록됐지만 `Effort`·`Type`·`Priority` 가 전부 비어 있다 — Status 만 채우고 끝낸 것이다.
- **이슈 close 와 Project Status 가 자동 연동이 아니다.** 손으로 옮기지 않으면 어긋난다.
- **문서에 없는 Project 필드**(`Importance`)가 생겨 있었고, 전 항목이 미입력이었다. 무엇을
  채워야 하는지 판단할 근거가 없었다.
- **라벨 `roadmap` 의 설명이 `docs/ROADMAP.md 항목`** 이었다. 그 파일은
  [ADR-0019](0019-remove-frozen-roadmap.md)로 삭제됐는데 라벨은 삭제된 파일을 계속 가리켰다.
- **릴리스 노트는 PR 라벨만 읽는다**([ADR-0020](0020-generate-release-notes-from-prs.md)). 이슈 라벨을
  정리해도 릴리스 준비가 되지 않는다는 사실이 절차로 적혀 있지 않아, v1.1.1 이후 PR 의 소급
  라벨링(이슈 #46)이 릴리스를 막는 상태로 남았다.

공통점은 **어느 하나도 실패로 드러나지 않는다**는 것이다. 이 저장소가 반복해 만난 사고 유형
(권한 `read` 로 리뷰가 사라진 #27·#30, 번호가 겹친 ADR #55→#56)과 같다. 조용한 누락은 규칙을
아는 것만으로는 막히지 않고, **매번 같은 순서를 밟아야** 막힌다.

## 결정 (Decision)

**GitHub 운영 절차를 `.claude/skills/github-ops/` 스킬로 둔다.** 진입점 `SKILL.md` 하나에서
들어가고, 상세 절차는 `references/` 에 나눈다(트리아지 · 계획 · 릴리스 · 감사 · 레퍼런스).

- **절차를 "읽기 → 브리핑 → 합의 → 일괄 실행" 으로 고정한다.**
  - 조회와 브리핑은 묻지 않고 한다.
  - **쓰기는 "무엇을 어떻게 바꿀지" 목록을 먼저 내고 승인받은 뒤 한꺼번에** 한다. 항목마다
    하나씩 묻지 않는다(대화가 산만해지고, 중간에 끊기면 절반만 적용된다).
  - 브리핑은 데이터를 나열하지 않고 **관리가 새는 지점 8가지**를 매번 점검한다(Project 등록
    누락 · 필드 미입력 · 상태 불일치 · PR 라벨 누락 · 마일스톤 · 서브이슈 다음 차례 · 릴리스
    시점 · 설정 드리프트).
- **우선순위·범위·릴리스 시점 같은 판단은 사용자에게 남긴다.** 스킬은 누락 탐지 · 형식 통일 ·
  명령 조립까지만 한다. 드리프트를 찾았을 때도 **어느 쪽이 맞는지 먼저 묻는다** — 문서를 설정에
  자동으로 맞추면, 실수로 바뀐 설정을 정당화하게 된다.
- **상태를 저장소에 복사해 두지 않는다.** 현황은 매번 `gh` 로 다시 읽는다. 스냅샷을 커밋하면
  동결된 `docs/ROADMAP.md` 와 같은 실수가 된다([ADR-0019](0019-remove-frozen-roadmap.md)).
- **역할을 셋으로 나눈다. 같은 내용을 두 곳에 적지 않는다.**

  | | 담는 것 | 답하는 질문 |
  |---|---|---|
  | [rules/github.md](../rules/github.md) | **현황** — 원격에 무엇이 켜져 있는가 | "필수 체크 이름이 뭐지?" |
  | `skills/github-ops/` | **절차** — 무엇을 어떤 순서로 하는가 | "이슈를 받았는데 뭘 해야 하지?" |
  | ADR | **근거** — 왜 그렇게 정했는가 | "왜 마일스톤을 쓰지?" |

  단 하나 예외를 둔다: 스킬은 **저장소 고유 사실 표**(Project #4 번호, 필드 ID, 필수 체크 이름,
  라벨→릴리스 노트 순서)를 자체적으로 갖는다. 절차를 실행하려면 그 값이 손 닿는 곳에 있어야
  하고, 매번 `rules/` 로 건너뛰게 하면 절차가 끊긴다. 대신 **그 표가 실제와 어긋나는 것 자체를
  감사 항목으로 넣어**(`references/audit.md`) 두 곳이 함께 갱신되도록 한다.

### 왜 rules/ 나 스크립트가 아닌가

- **`rules/` 가 아닌 이유**: `rules/` 는 저장소를 **편집할 때의 가드레일**이고 CLAUDE.md 를 통해
  사실상 항상 로드된다. GitHub 운영 절차는 분량이 크고(다섯 문서) **필요할 때만** 필요하다.
  스킬은 호출 시점에 로드되므로 평소 컨텍스트를 늘리지 않는다.
- **`scripts/*.ps1` 이 아닌 이유**: 이 일은 **판단이 필요**하다. "이 이슈를 무슨 라벨로 볼 것인가",
  "지금 릴리스할 시점인가" 는 결정론적으로 계산할 수 없고, 자동화하면 사용자의 결정을 대체해
  버린다. `doctor.ps1` 처럼 규약 위반을 기계적으로 세는 일과 성격이 다르다. 게다가 `gh` 인증과
  네트워크에 의존하므로 `check.ps1` 게이트에 넣기에도 부적절하다.
- **스킬을 여러 개로 쪼개지 않은 이유**: 진입점이 여럿이면 이름을 외워야 하고, 상태 수집 로직이
  중복된다. 무엇을 할지는 **브리핑을 본 뒤에** 정해지는 게 자연스럽다.

## 결과 (Consequences)

- **좋은 점**: 조용한 누락이 절차에 걸린다. "Project 등록 → 필드 입력" 처럼 잊기 쉬운 두 번째
  단계가 문서에 박혀 있고, 브리핑이 미입력 항목을 매번 다시 들춘다.
- **좋은 점**: 원격 설정과 문서의 드리프트를 **찾는 방법**이 생겼다. 지금까지
  [rules/github.md](../rules/github.md) 는 갱신을 사람의 기억에 의존했다.
- **좋은 점**: 판단과 실행이 분리되어, 되돌리기 비싼 작업(릴리스 태그, 이슈 close)이 승인 없이
  일어나지 않는다.
- **좋은 점**: `gh` 명령의 실전 함정(GraphQL 여러 줄 쿼리 실패, 서브이슈 API 가 번호가 아니라
  database id 를 받음, 한국어 본문은 `--body-file` 로)이 한곳에 모였다.
- **감수할 점**: **CI 가 이 스킬을 검증하지 않는다.** `gen-docs-index.ps1 -Check` 는 ADR · rules ·
  `docs/scripts` 만 본다([ADR-0021](0021-generated-doc-index.md)·[ADR-0022](0022-per-script-docs.md)).
  스킬 안의 필드 ID 나 라벨 목록이 낡아도 자동으로는 잡히지 않는다 — 감사 절차를 **주기적으로
  실제로 돌리는 것**만이 방어책이다.
- **감수할 점**: 저장소 고유 사실이 두 곳(스킬 표 · `rules/github.md`)에 존재한다. 의도한
  중복이지만, 한쪽만 고치면 어긋난다. 그래서 감사 항목에 넣었다.
- **감수할 점**: 문서가 다섯 개 늘었다. 절차를 늘리는 것으로 해결하려는 유혹이 생기면, 이
  ADR 의 전제를 다시 봐야 한다 — **막으려는 것은 조용한 누락이고, 늘려야 하는 것은 규칙이
  아니라 반복 가능한 순서다.**
