# 계획 — 마일스톤 · 서브이슈 · 큰 일 쪼개기

이슈 하나로 끝나지 않는 일을 다루는 절차. 축이 셋이고 **서로 대체하지 않는다.**

| 도구 | 무엇의 단일 소스인가 | 언제 |
|------|---------------------|------|
| **Project #4** | 항목 단위 상태 (Status·Effort·Type·Priority) | 로드맵 항목이면 **항상** |
| **마일스톤** | 완료 기준을 공유하는 이슈 묶음의 **진척률 N/M** | 여러 이슈가 모여야 목표가 끝날 때 |
| **서브이슈** | 부모 하나를 **순서대로** 끝내는 파트 목록 | 한 이슈가 여러 PR 로 갈릴 때 |

근거: [ADR-0024](../../../adr/0024-milestones-for-cross-cutting-goals.md)(마일스톤) ·
[ADR-0016](../../../adr/0016-track-in-github-not-docs.md)(추적은 GitHub 으로).
**로드맵의 단일 소스는 여전히 Project 다** — 마일스톤이 그 자리를 대신하지 않는다.

## A. 마일스톤을 만들까

### 만드는 경우 — 세 조건을 모두 만족할 때만

1. 하나의 목표를 위해 **여러 이슈가 필요**하다.
2. 그 이슈들이 **공통 완료 기준**을 공유한다("3-OS 에서 똑같이 돈다").
3. **진척률(N/M)** 이 알고 싶은 정보다.

예: [#1 크로스 플랫폼 지원](https://github.com/Chigo55/Docker-Compose/milestone/1) — 셸 런타임 ·
경로 처리 · 바인드 마운트 권한 · CI 3-OS 매트릭스 · 인코딩 규약 · 문서 문구로 갈라지고,
어느 하나만 끝나도 목표는 안 끝난다.

### 만들지 않는 경우

- **단일 이슈로 끝나는 일** → Project 항목만으로 충분하다.
- **완료 기준 없는 주제 묶음** ("문서 개선 전반") → 그건 **라벨**이 하는 일이다.
- **릴리스 버전 통** ("v1.2.0" 마일스톤) → 노트는 PR 라벨에서 자동 생성된다([ADR-0020](../../../adr/0020-generate-release-notes-from-prs.md)).

### 만들 때

**완료 기준은 마일스톤 설명에만 둔다.** 소속 이슈가 복사하지 않는다 — 복사하면 기준이 갈린다.

```bash
gh api repos/:owner/:repo/milestones -f title="<목표>" -f description="<완료 기준>"
gh issue edit 59 60 61 62 63 64 65 --milestone "크로스 플랫폼 지원 (Windows · macOS · Linux)"
gh api repos/:owner/:repo/milestones --jq '.[] | "#\(.number) \(.title) \(.closed_issues)/\(.open_issues + .closed_issues)"'
```

마일스톤에 넣은 이슈도 **Project 등록은 별도**다([triage.md](triage.md#5-project-4-등록--이슈-생성과-별개-단계다)).
둘 다 해야 브리핑 점검 1번·5번을 통과한다.

## B. 큰 이슈를 파트로 쪼개기

Project `Effort=L` 이거나, 한 PR 에 담으면 리뷰가 불가능해지는 이슈가 대상이다.

### 쪼개는 축 — 파일이 아니라 **되돌릴 수 있는 단위**로

각 파트는 **그것만 병합해도 저장소가 성립**해야 한다. `check.ps1 -Test` 가 통과하고, 문서가
반쪽이 아니어야 한다. 파일별로 나누면 이 조건이 깨진다.

파트에 기호를 붙여 순서를 드러낸다 — 이 저장소는 `C.2`·`C.3` 형태를 쓴다(#50 → #52·#53).

### 첫 파트만 PR, 남은 파트는 서브이슈로

작업을 시작하면 **첫 파트만 PR 로 내고**, 남은 파트는 부모 이슈의 **순서 있는 서브이슈**로
등록한다. 한 PR 에 전부 담아 리뷰를 마비시키지 않고, 남은 일을 대화 밖으로 내보내
세션이 끊겨도 살아남게 한다.

### 서브이슈 등록 — `number` 가 아니라 `id` 를 넘긴다

REST API 는 이슈 번호가 아니라 **database id** 를 받는다. 번호를 넘기면 엉뚱한 이슈가 붙거나
404 가 난다. 반드시 id 를 먼저 조회한다.

```bash
# 1) 자식 이슈의 database id 조회 (← 번호가 아니다)
gh api repos/:owner/:repo/issues/53 --jq .id

# 2) 부모(#50)에 자식으로 등록
gh api repos/:owner/:repo/issues/50/sub_issues -f sub_issue_id=<위에서 얻은 id>

# 3) 확인 — 부모의 서브이슈 목록과 상태
gh api repos/:owner/:repo/issues/50/sub_issues --jq '.[] | "#\(.number) [\(.state)] \(.title)"'
```

### 부모 이슈 본문에 파트 목록을 적는다

서브이슈 관계는 GitHub UI 에서 보이지만, **왜 그 순서인지**는 본문에만 남는다.

```markdown
## 파트
- [x] C.2 — docs/scripts/ 로 사용법 분리 (#52)
- [ ] C.3 — CLAUDE.md 집약 영역 지역화 (#53)   ← 다음 차례
- [ ] C.4 — ...

C.2 가 먼저인 이유: 인덱스 생성기가 자리를 잡아야 C.3 에서 CLAUDE.md 의 목록을 지울 수 있다.
```

부모는 **모든 파트가 닫힐 때까지 열어 둔다.** 부모를 먼저 닫으면 남은 파트를 찾을 입구가 사라진다.

## C. "지금 뭐 할까" 에 답하기

사용자가 다음 작업을 물으면, 아래 순서로 후보를 좁혀 **2~3개만** 제시한다. 열린 이슈 전체를
나열하지 않는다.

1. **차단 요소** — 다른 일을 막고 있는 것. (예: #46 소급 라벨링은 v1.2.0 릴리스를 막는다)
2. **진행 중 묶음의 다음 파트** — 부모 이슈의 열린 서브이슈. 시작한 일을 끝내는 것이 먼저다.
3. **마일스톤 진척** — 열린 마일스톤에서 `Effort=S` 인 것. 진척률이 눈에 보이게 움직인다.
4. **선행 의존** — ADR 결정이 다른 이슈를 막고 있는 경우. (예: #59 셸 런타임 정책이 #60~#65 의
   전제)

각 후보에 **왜 지금인지 한 줄**과 **예상 규모(Effort)** 를 붙인다. 그다음 사용자가 고른다.
